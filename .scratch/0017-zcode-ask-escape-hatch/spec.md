# 0017 — zcode ask 逃生舱：宿主三按钮之外补「本会话都拒绝」与附理由说明

> Status: ready-for-agent
> 决策依据：ADR-0019；grill-log Round 14（窄口径重开 Q11）。

## Problem Statement

用户在 zcode 中使用 auto-guard 时，删除类等命令触发守卫 ask，宿主原生确认框只提供三个按钮：同意 / 本会话都同意 / 拒绝。用户面临两个缺口：

1. **没有「本会话都拒绝」**——用户已经决定"这类命令本会话都不要执行"，宿主却每次都重新弹窗、每次都要再点一次拒绝；守卫侧对"用户拒绝过"毫无记忆。
2. **没有附理由说明需求的入口**——用户拒绝时想说"我要的其实是 X，别用这种方式"，弹窗里没有任何文字输入；守卫拒绝后模型收到的只是一个笼统的"用户拒绝了权限"，无法据此调整方案。

弹窗本身不可扩展：hook 出线协议是严格 schema，hook 是无 TTY 子进程，三个按钮由 zcode 宿主渲染。缺口必须在守卫自有通道上补齐。

## Solution

在宿主弹窗**之外**接通四态记忆的后两态（allow-session / deny-session）与理由通道：

- 守卫每次 ask 出线时，旁路落盘一条 pending ask 记录（命令原文、风险、时间、会话键），宿主弹窗照旧，出线协议逐字节不变。
- 用户在另一个终端用 `auto-guard guard ask` 查看待裁决列表，选择**本会话放行**或**本会话拒绝（可附理由）**；裁决写入会话缓存，本会话内同类命令不再弹窗。
- 本会话拒绝的后续命中，用户附的理由会作为拒绝理由送达模型上下文——这就是"向 agent 说明需求"的闭环：拒绝后在对话里说明需求，模型按理由调整；且模型会在 ask 时预先收到守卫的指引（拒绝后按理由调整、不要原样重试）。
- ask 原因文案末尾追加一行提示，告诉用户出路在哪里。

## User Stories

1. 作为 zcode 用户，我想在守卫 ask 后通过一条 CLI 命令让同类命令本会话都拒绝，所以同一类命令不再反复弹窗。
2. 作为 zcode 用户，我想在拒绝一条 pending ask 时附上原因文字，所以模型后续收到拒绝时知道我真正要什么。
3. 作为 zcode 用户，我想在守卫 ask 后通过 CLI 让同类命令本会话都放行，所以已知安全的命令本会话内静默通过。
4. 作为 zcode 用户，我想看到当前所有待裁决的 ask 列表（命令、风险、时间、来源工作区），所以我能在多条之间准确选择。
5. 作为 zcode 用户，我想在宿主弹窗的原因文案里直接看到"本会话记住/附理由"的出路提示，所以我不需要翻文档才知道怎么表达本会话决定。
6. 作为 zcode 用户，当我选拒绝并在对话里说明需求时，我希望模型收到守卫的预指引（按理由调整、不要原样重试），所以对话不需要我重复解释。
7. 作为 zcode 用户，我希望裁决命令自身不被守卫拦截弹窗，所以逃生舱不会套娃。
8. 作为 zcode 用户，我希望裁决写入的记忆随会话结束自动消失，所以"本会话"语义保真、不产生永久副作用。
9. 作为 zcode 用户，我希望对一个命令重复触发 ask 时只留一条待裁决记录，所以列表不会被刷屏。
10. 作为 zcode 用户，当我想裁决的记录已过期消失时，我希望得到明确的报错而不是静默失败，所以我知道该重新触发一次 ask。
11. 作为多宿主用户，我在 pi 上的四态对话框体验不变，所以这次改动不回归既有交互。
12. 作为 codex 用户，我收到的 deny 翻译行为不变，所以 headless 兜底语义不受影响。
13. 作为 claude/qoder 用户，我也希望获得同样的待裁决列表与提示文案，因为三个 hook 宿主共享同一限制。
14. 作为守卫的 agent（模型），我在 ask 时收到的上下文应说明"用户拒绝并给出理由时按理由调整"，所以我不会机械重试同一条命令。
15. 作为守卫的 agent（模型），当用户表示"本会话都拒绝这类命令"时，我希望知道可以运行 `guard ask deny --reason` 记入会话记忆，所以我能替用户完成记忆操作。
16. 作为运维者，我希望 pending 记录随会话目录的既有剪枝机制一起清理，所以不新增需要手工维护的状态文件。
17. 作为运维者，我希望落盘失败不影响 ask 出线（守卫主职能不受旁路记录影响），所以故障面不扩大。
18. 作为关注隐私的用户，我的理由文字只落在本机会话目录，不外发，所以表达需求没有泄露面。

## Implementation Decisions

- **门控**：落盘、提示文案、模型预注射三者门控在「默认 hookSpecificOutput 方言的 native ask 宿主」（zcode / claude / qoder，共享谓词 `hasAskEscapeHatch`：native askStyle + headlessFallback 'host' + 无自定义 wire）；pi（four-state，进程内四态对话框）、codex（ask→deny 翻译，且其 askStyle 是 one-shot）、opencode（自有 verdict wire）逐字节零变化。
- **作用范围**：提示与预注射只挂在**可解析**的 ask 上（守卫拿到了待裁决命令/路径的 guardable 请求，且记录确实落盘）；unreviewable（tool_input 不可读）与 fail-closed 初始化失败类 ask 没有可解析对象，不落盘、不加提示——提示指向一个空列表是误导。
- **pending ask 记录**：写入各会话目录（对齐既有 pending-deletes 先例的形态）；键为既有会话键构建函数的输出（会话 + 工作区 + 命令全文；文件工具取目标路径），与四态记忆写入键全等；字段含命令原文、风险、原因、时间戳、键；同键 upsert 并触碰时间戳；读侧按时间升序供 CLI 列表。写失败静默——旁路记录不得影响裁决出线。
- **裁决写入**：复用 `rememberAsk` 的会话缓存语义（经共享的 `sessionMemoryEntry`：会话级有效、不设过期时间戳），随会话目录既有 24h 剪枝自然消亡；键全等保证下一条完全相同的命令必然命中。文件工具在 `decideFile` 敏感路径门**之前**查会话记忆（通用管线语义，见 ADR-0019 Consequences：pi 至今不写文件路径条目，实际行为不变）。
- **CLI 面**：`guard ask list / allow <n> / deny <n> [--reason]` 挂入共享管理 CLI，三个 hook 宿主免费获得；once 两态宿主弹窗已覆盖，CLI 不重复；条目已消失时非零退出并明确报错；输出走既有双语消息目录（ADR-0011 四层，标点归目录）。
- **模型预注射**：ask 出线时经协议已有的 `additionalContext` 字段附带指引（ZCode 官方 hook 文档核实其注入对话且与 permission decision 共存）；仅 ask 结果附带，deny/allow 不带。
- **提示文案**：双语目录新增一条 ask 逃生舱提示消息，追加在 ask 原因文末（仅当记录落盘成功）。
- **自放行（窄口径）**：出厂规则只放行 `auto-guard guard ask list`（只读）与 `auto-guard guard ask deny *`（只降权）；`allow`、`guard on/off`、`node <路径>` 直跑形态一律不放行——被守卫的代理不能给自己发许可，跨段 `*` 匹配不得构成代码执行洞（黑名单优先级不变）。逃生舱的 list/deny 命令被守卫拦出 ask 属套娃缺陷。
- **出线协议**：宿主收到的 stdout 除 reason 文末多一行提示与 ask 场景的 additionalContext 外逐字节等价；zcode 的 wire 与能力声明不动。

## Testing Decisions

- 好测试只断言外部可见行为：hook 进程的出线字节、磁盘上的记录/缓存状态、CLI 的输出与退出码；不测内部函数拆分。
- **最高缝（hook 出线）**：经既有 hook 宿主测试入口注入 stdin/stdout 与 fixture home，断言 ask 出线字节（含提示行与 additionalContext）、pending 记录 upsert/触碰、落盘失败不影响出线、pi/codex 宿主零变化。先例：host-zcode 的 hook-output 与 runtime-contract 契约测试、host-runtime 的参数化契约套件。
- **CLI 缝**：经既有 CLI 测试入口注入 fixture 配置根，断言列表渲染、裁决后缓存可查且键与 `rememberAsk` 全等、stale 条目报错、多会话列表。先例：cli 包 shell 测试。
- **core 缝**：会话缓存命中路径单测——裁决后完全相同的命令命中会话缓存。先例：ask-memory、commands 规格。
- 全链路验收（工单 03）：真实 zcode 会话手动验证——ask → CLI 拒绝附理由 → 完全相同的命令不再弹窗且模型收到理由。

## Out of Scope

- 宿主弹窗内的任何改动（按钮、输入框）——协议约束下的最终形态，文档如实写明。
- 持久规则管理（rules.json 的用户规则增删）——独立特性，且违背"运行中命令隐式写用户所有物"的显性化立场（ADR-0008/0013）。
- 形状级命令键匹配（同一类但文本不同命中同一条记忆）——v1 全文键与 `rememberAsk` 一致；SPEC 0007 近邻匹配先例是后续研究方向。
- TUI 展示待裁决列表——CLI 优先，视使用反馈再立项。
- pi / codex 行为变化；PermissionRequest hook 事件接入。

## Further Notes

- 本 spec 窄口径重开 grill-log Q11：「ask 委托宿主原生弹窗」的出线方式与能力声明不变，变的是弹窗外的守卫自有通道。
- 理由文字以明文存于本机会话目录，与会话缓存既有 reason 字段同级别，无新增泄露面。
- 宿主「本会话都同意」按钮写的是宿主自有 allowlist，与守卫会话缓存是两层，互不读写（ADR-0015 已接受宿主层放行绕过守卫）。
