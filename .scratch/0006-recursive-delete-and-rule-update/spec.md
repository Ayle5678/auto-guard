# 0006 — 递归删除不变式判定 + init 显式规则更新

Status: done

## Problem Statement

在 Qoder 实测中发现：agent 跑裸 `rm -r <目录>`（不带 `-f`）时，auto-guard 的目录删除复核流完全没有触发——命令落入 `unknown` 类别，被 LLM 以 low risk 放行，且放行结果写入了 30 天持久缓存；同一命令在缓存有效期内重放将免审直行。对用户来说，"删除目录必须给理由、复核恰好一次、永不缓存"这条安全承诺对最常见的递归删除拼法失效。

止血已完成（出厂规则补 `rm -r *` / `rm --recursive *` 枚举，回归测试钉死），但暴露两个结构性问题：

1. **枚举判定追不完拼写**：`rm -f -r`、`rm -rF`、`rm -Rf` 等 flag 排列仍会漏，每多一种写法就要多一条手写规则，组合发散。
2. **新出厂规则到不了存量安装**：规则双层文件下用户字段整体胜出、只补整段缺失的顶层字段，本次止血需要在本机三宿主手工同步六份文件。没有升级通道的修复，对存量用户等于没修。

## Solution

两个独立但同源的结构性改进（决策记录：ADR-0012、ADR-0013）：

1. **递归删除按不变式判定**：把"递归删除"的判定从拼写枚举升级为一条不变式——`rm` 携带任意拼写的递归 flag（短 flag 聚簇含 `r`/`R`，或整词 `--recursive`）即走目录删除复核流。实现为既有数据驱动守卫机制（staticAllowGuards 的 `when` + token flag 结构）扩展**短 flag 聚簇分解**语义，数据仍住 rules.json，每宿主可编辑。
2. **init 显式规则更新**：安装器 `init` 检测出厂默认含本地缺失的模式时，展示 diff 预览，用户确认后按「幂等追加 + 去重 + 写前备份」写入配置根的两层规则文件；拒绝则原样。运行时加载行为**不变**（永不静默合并）。

不做 AST / shell 解析器（ADR-0012 拒绝项：core 零 npm 依赖约束、判定是词汇问题非句法问题、解析失败仍需 LLM 兜底、变量替换类场景 AST 无解且本就归 LLM）。

## User Stories

1. 作为在宿主中使用 agent 的用户，我希望 `rm` 携带任何拼写的递归 flag（`-r`、`-R`、`-rf`、`-fr`、`-f -r`、`-rF`、`--recursive`）时都触发目录删除复核流，以便删除目录的每一拼法都"先拒一次、给理由重试、LLM 复核恰好一次、永不缓存"。
2. 作为在宿主中使用 agent 的用户，我希望 `rm notes.txt` 这类普通文件删除不受不变式影响，以便日常清理文件不被无谓打断。
3. 作为在宿主中使用 agent 的用户，我希望 flag 拼写漏网时的残余风险只有"多一次 LLM 审查"而非"静默放行并被缓存"，以便安全网的失效方向是保守的。
4. 作为 agent，我希望递归删除被拒时收到明确的 `[删除理由]` 重试指引，以便我能在下一次调用中给出理由完成删除。
5. 作为 auto-guard 的存量用户，我希望运行 `auto-guard init` 时能看到"出厂默认新增了哪些我本地缺失的规则"的 diff 预览，以便我知情地决定是否接受。
6. 作为 auto-guard 的存量用户，我希望接受规则更新后，defaults.json 与 rules.json 两层都只追加缺失条目、已有内容一字不动，以便我的自定义规则永不被动。
7. 作为 auto-guard 的存量用户，我希望规则更新写盘前自动备份、重复运行幂等、`remove` 卸载不受影响，以便任何一步都可回退。
8. 作为 auto-guard 的存量用户，我希望拒绝规则更新后工具不再纠缠，以便我保持旧规则持续运行。
9. 作为脚本化安装的用户，我希望规则更新提供非交互入口（接受/拒绝都可显式指定），以便无人值守环境不卡在交互提示。
10. 作为宿主适配层维护者，我希望递归删除判定完全由 core 规则数据驱动，以便六个宿主零改动获得同一不变式。
11. 作为 AFK 实施工单的 agent，我希望"聚簇分解"语义有精确的验收样例表（命中/不命中各一列），以便我不需要猜边界。
12. 作为 code reviewer，我希望分类器的类别优先序（hard-deny → directory-delete → always-review → …）保持不变，以便本次改动不扰动其他类别的既有裁决。

## Implementation Decisions

- **判定不变式（ADR-0012）**：新增一个数据驱动的守卫结构（与 staticAllowGuards 同族）：`when` 锚定 glob（如 `rm *`）+ 递归 flag 描述。flag 匹配两层语义：整词精确（`--recursive`、`--recursive=x` 形态沿用现有 `=` 前缀处理）+ **短 flag 聚簇分解**（`-xyz` 形态按字母拆开，含 `r` 或 `R` 即命中）。大小写不敏感沿用现有 glob 语义。
- **数据住 rules.json**：新守卫结构是 `RulesFile` 的新顶层字段（出厂默认含一条 `rm` 规则），每宿主可编辑、可删除。现有 `directoryDelete` / `alwaysReview` 的枚举条目**原样保留**（旧安装的规则文件继续有效，新机制是加法不是替换）。
- **类别优先序不变**：守卫命中后归入 `directory-delete` 类别，`classifySimple` 的既有判定顺序不动；命中点放在 directoryDelete 枚举匹配之后、alwaysReview 之前（同族语义：更严类别优先）。
- **显式规则更新（ADR-0013）**：`init` 在播种完成后增加一步：对比出厂默认与本地两层规则文件，找出"出厂有、本地无"的模式条目（按清单去重对比），展示 diff 预览；确认后幂等追加（`*.auto-guard.bak` 写前备份）；提供非交互 flag（更新/跳过二选一显式指定）供无人值守。拒绝则完全不动文件。
- **运行时加载行为不变**：`mergeMissingRuleFields` 的"只补整段缺失顶层字段"语义保持；本 ADR 系列不引入加载期合并。
- **零依赖不变**：core 与安装器均不新增 npm 运行时依赖；不引入 shell 解析器。
- **文案双语**：安装器新增的预览/确认/跳过提示进消息目录，中英键类型强制对齐（ADR-0011 机制）。
- **本机现状**：pi/qoder/zcode 三宿主六份规则文件已手工补入 `rm -r *` / `rm --recursive *` 并清除毒缓存条目（2026-08-29，即显式更新流程的首次人工执行）；不回滚，工单验证时作为行为参照。

## Testing Decisions

- **只测外部行为**：断言分类结果与守卫命中与否、安装器执行后文件的实际内容（追加条目、已有行原样、备份文件存在、幂等重跑无变化、拒绝时文件不变），不断言内部函数划分。
- **core 侧**（现有缝，不建新缝）：规则模块单测——先例是 staticAllowGuards 的匹配测试（含 `-describe` ≠ `-d` 的边界样例风格）；验收样例表驱动：命中列（`rm -r x`、`rm -R x`、`rm -rf x`、`rm -f -r x`、`rm -rF x`、`rm --recursive x`）与不命中列（`rm x`、`rm -i x`、`git branch -r`、`echo "rm -r x"`）。
- **core 侧端到端**：GuardService 测"裸/排列 rm 走目录删除理由流且不写持久缓存"——先例正是本次止血的回归测试（先红后绿）。
- **cli 侧**（现有缝）：安装器测试先例（写文件、备份、幂等、卸载断言）扩展出规则更新步骤的同族断言。
- **本机三宿主**为手工验证参照，不进自动化。

## Out of Scope

- shell AST / 解析器；变量替换场景（`X='-rf'; rm $X`）——归替换检测 + LLM 兜底。
- 规则删除/墓碑语义（用户删掉的出厂模式如何不被更新复活）——显式 diff 预览即当前答案，需要更细语义时另立 feature。
- `find -delete`、`git clean` 等非 rm 删除途径——已有 staticAllowGuards 覆盖，不在本期。
- 存量安装的静默/自动迁移——ADR-0013 明确拒绝。
- 六宿主适配层改动——本 spec 全部落在 core 规则模块与 cli 安装器，宿主零改动。
