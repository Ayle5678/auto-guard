# 0016 — 缓存容量与写入策略（1100 = 100 会话 + 1000 跨会话）

Status: done（2026-08-31 当日交付：4 工单全部完成，容量 100+1000、合并语义、历史层停写、文档同步）

## Problem Statement

用户面对两个问题。其一，持久缓存（跨会话缓存）目前没有任何容量上限，只在 TTL 到期时剪枝：命令种类随时间只增不减，缓存文件无限膨胀，新学到的放行结论与半年前的一次性命令混在一起，容量不可预期。其二，缓存写入没有聚焦：历史判断层命中（本地审计库已能免 LLM 放行）还会占用会话缓存槽位；静态放行、学习规则命中等毫秒级快速路径本就不写缓存，但这一写入策略没有被测试钉死，容易被回归破坏。缓存槽位是稀缺资源（每条都对应一次免审机会），应当只留给「除了规则、学习规则、历史命中之外」的结论——即 LLM 兜底审出的放行与用户 ask 四态的人工选择。

## Solution

把两级缓存的默认容量定为 1100 条：会话缓存 100 条（现默认 256），跨会话持久缓存 1000 条（现无上限）。持久缓存满员后按 LRU 逐出：命中即刷新 `lastHitAt`，逐出最久未被使用（无 `lastHitAt` 回退 `cachedAt`）的条目。合并语义显式化并测试钉死：两类缓存均按「工作区×命令」精确 key 存储，完全相同的命令再次写入/命中时刷新既有条目（续期 TTL、刷新近期度），绝不堆叠重复条目。写入策略收紧为：只有 LLM 兜底审出的 allow、用户 ask 四态选择、以及持久缓存命中向会话缓存的提升（同一 key 刷新，不占新槽）会写缓存；历史层命中停止写会话缓存（重复命中改为每次重查本地审计库，毫秒级代价换取会话缓存槽位全部留给 LLM 审出的结论）。

## User Stories

1. 作为长期使用 auto-guard 的开发者，我希望持久缓存有 1000 条上限，以便缓存文件大小可预期、不会随使用时长无限膨胀。
2. 作为频繁重复同类命令的开发者，我希望最近仍在使用的命令在缓存满员时不被逐出，以便热命令持续免审。
3. 作为很少回头的旧命令的所有者，我希望最久未命中的条目先被逐出，以便 1000 个槽位始终留给还有价值的结论。
4. 作为关心缓存内容质量的开发者，我希望历史层、静态放行、学习规则命中的结论不占用缓存槽位，以便缓存只积累 LLM 审出的新知识。
5. 作为在同一会话里反复跑相同命令的开发者，我希望完全相同的命令在缓存里只有一条且每次命中都刷新它，以便不出现重复条目、热条目不被误逐出。
6. 作为在同一工作区多次批准同一命令的开发者，我希望重复批准只续期既有条目而非新增，以便容量计数按「不同命令数」而非「命中次数」增长。
7. 作为 hook 宿主（每命令一个新进程）的用户，我希望命中持久缓存时的近期度刷新落盘，以便 LRU 信号跨进程存活、逐出不退化为 FIFO。
8. 作为开启审计库与历史层的用户，我希望历史层命中不再写会话缓存，以便会话缓存 100 条全部留给需要记忆的结论；我接受重复命令每次重查一次本地 SQLite 的毫秒级代价。
9. 作为会话内多次触发目录删除复核或 LLM deny 的用户，我希望 ask 四态选择与 Guard Memory 记忆照旧写入会话缓存，以便人工决定在本会话内持续生效。
10. 作为使用 DSH/Pi 进程内宿主的用户，我希望会话缓存默认 100 条对内存实现同样生效，以便各宿主行为一致。
11. 作为手工编辑 config.json 的高级用户，我希望新增 `persistentCacheSize` 配置键（默认 1000）并自动补齐进存量配置，以便我可以按需调大调小。
12. 作为存量用户，我希望升级后配置文件自动补上 `persistentCacheSize`、`sessionCacheSize` 保持用户已改过的值，以便零迁移、旧值不被覆盖。
13. 作为命令管道/复合命令的使用者，我希望子命令级缓存写入仍按各自类别判定（cacheable/unknown 的 LLM 放行才写），以便复合命令的缓存行为与单命令一致。
14. 作为维护者，我希望「快速路径命中不写缓存」成为被测试钉死的不变量，以便未来改动不引入回归。
15. 作为阅读文档的用户，我希望双语 README 的配置表反映新默认值与新键、术语表反映历史层不再写缓存，以便文档与行为一致。

## Implementation Decisions

- **容量**：`sessionCacheSize` 默认 256 → **100**（core 默认值与 host-dsh 的默认值拷贝同步改；`SessionLruCache`/`DiskSessionCache` 构造器兜底默认同步对齐 100）。新增配置键 **`persistentCacheSize`**（默认 **1000**），进 `GuardConfig`、CONFIG_KEYS 与 DSH 字段表；存量配置由既有「缺失字段补齐回写」机制自动获得。
- **持久缓存上限与 LRU**：`PersistentCache` 构造函数加可选 `maxEntries`（默认 1000）。`CacheEntry` 增可选 `lastHitAt`；`get()` 命中即刷新 `lastHitAt` 并落盘（hook 宿主每命令新进程，不落盘则 LRU 退化为 FIFO）。`set()` 时若超过 `maxEntries`，逐出 `lastHitAt ?? cachedAt` 最旧的一条再插入。TTL 剪枝逻辑不变，save 时照旧过滤过期条目。
- **合并同类项**：不变量 = 每个「工作区×命令」key 至多一条，重复 `set` 覆盖刷新（cachedAt/expiresAt 续期、LRU 位置更新），命中刷新 `lastHitAt`。此语义现在已基本成立，本次以测试钉死并补上命中刷新。会话缓存（内存/磁盘两实现）同理。
- **写入策略（只记录规则、学习规则、历史命中之外）**：历史判断层命中**停止写会话缓存**（删除该处唯一调用）；静态放行、预授权、学习规则（模板缓存命中）本就不写，补测试钉死为不变量。LLM 兜底 allow（cacheable/unknown、非 high 风险）照旧写会话+持久；always-review 的 LLM allow 照旧只写短 TTL 会话缓存；ask 四态选择照旧写会话缓存；Guard Memory 不变。持久缓存命中向会话缓存的**提升保留**——它是同一 key 的会话内复制刷新，不产生新的不同命令条目，也不在用户的排除清单内。
- **接线点**：`PersistentCache` 的三个组装点（host-runtime bootstrap、host-dsh、host-pi）传入 `config.persistentCacheSize`；conformance 测试的构造点同步。
- **无新 ADR**：不新增接缝、不触碰宿主耦合边界（ADR-0002 纪律内），决策记录于本 spec；CONTEXT.md「历史判断层」词条（「只写会话缓存」→「不写任何缓存」）与 README 双语配置表（`sessionCacheSize` 默认值、新增 `persistentCacheSize` 行）随工单同步。

## Testing Decisions

- 只测外部行为：经 `GuardService.decide()`（ADR-0002 注入缝）断言裁决结果与注入缓存中的副作用（是否写入、写入几条）；缓存组件直接断言容量/合并/逐出/近期度刷新行为，不窥内部结构。
- 好测试标准：不依赖实现细节（如私有字段），断言用户可见语义——「重复命令缓存里仍只有一条」「满员后最久未用者先走」「历史命中后紧接着的重复命令仍走历史层而非会话缓存」。
- 先例：`packages/core/tests/cache.spec.ts`（容量/逐出）、`session-store.spec.ts`（磁盘版）、`guard-service-history.spec.ts`（历史层行为——其「history hit 写 session cache」断言按新策略改写）、`guard-service.spec.ts`（LLM 放行写双缓存的既有断言保持通过）。
- 宿主接线：host-runtime `guard-deps.spec.ts`、conformance 构造点参数化已覆盖；DSH 默认值拷贝改动由其既有 config 测试兜底。

## Out of Scope

- 模板缓存（学习规则载体）的容量与逐出策略不动。
- 决策历史 JSONL 环形文件的上限不动。
- 不做跨宿主缓存共享/导入导出（grill-log 既有决策：仅未来 opt-in）。
- 不改 TTL 数值、历史层/学习规则阈值、复合命令拆分语义。
- 不做会话缓存按宿主差异化容量；进程内宿主多会话共享 100 条 LRU 的场景不做特殊处理（容量是用户可调配置）。

## Further Notes

- 「1000 条跨会话」按配置根计：持久缓存文件本就按宿主配置根隔离（ADR-0003），工作区隔离由 key 前缀承担，1000 是整文件上限而非单工作区上限。
- 历史层停写会话缓存的代价：开启 `historyEnabled` + `examineEnabled` 的用户，重复命令每次重查一次本地 SQLite（毫秒级）；换来的是会话缓存槽位语义纯粹（只装 LLM 审出与人工选择）。
- 逐出写盘频率：命中即刷新 `lastHitAt` 意味着持久缓存命中会多一次小 JSON 落盘（约百 KB 量级）；相对被省掉的 LLM 秒级调用可接受，不做合并写批处理（过度设计）。
